# 009 — Continuous integration

**Status:** Built · **Updated:** 2026-10-20

## Proposal

Every push builds and tests the repo somewhere other than dev-lnx01. Three specs already lean on
this: correctness on ARM (notes 006 and 008: x86's strong ordering hides missing barriers that
aarch64 exposes), cross-process correctness that TSan cannot check (note 008), and "builds for
aarch64" checked only by cross-compiling, never run.

It does:

- build with warnings as errors and run the test suite on x86-64 and aarch64, on every push and
  pull request;
- run the suite under ThreadSanitizer, and under AddressSanitizer with UBSan, on x86-64;
- run `run.py report --check`, so a stale README or RESULTS fails CI as it fails CTest;
- make the tests run on a machine that is not dev-lnx01 (fewer CPUs, one NUMA node, shared and
  noisy).

It does not:

- run benchmarks or produce results. Published numbers come from dev-lnx01 in bench mode only;
  a shared cloud VM's figures mean nothing;
- use a self-hosted runner on dev-lnx01 (see Design);
- add a test framework, coverage, or release packaging.

## Design

**Runners: GitHub-hosted, x86-64 and arm64.** Checked 20 Oct 2026: arm64 standard runners
(`ubuntu-24.04-arm`) are available to private repositories since January 2026. In a private repo
both have **2 vCPUs** (4 once public). Free accounts include 2,000 minutes a month for private
repos; public repos are free. A self-hosted runner on dev-lnx01 is rejected: CI jobs would run on
the benchmark machine and perturb it, and once the repo is public a self-hosted runner executes
code from anyone's pull request.

**Toolchain: the `ubuntu:26.04` container on both runners.** The runner images are Ubuntu 24.04;
dev-lnx01 is 26.04 and its gcc 15.2, CMake 4.2.3, Ninja 1.13, Python 3.14 and binutils 2.46 are
all from the 26.04 archive. The official image exists for amd64 and arm64 (updated 17 Oct 2026),
so `apt install` in the container gives CI the same compiler as the measured binaries. Installing
takes a minute or two per job; a prebuilt image is not worth maintaining yet.

**Jobs.** Four per push:

| Job | Arch | Build | Runs |
|---|---|---|---|
| `x64` | x86-64 | Release, baselines | full suite, `check_hot_path`, `report --check` |
| `x64-tsan` | x86-64 | `-fsanitize=thread`, no baselines | suite |
| `x64-asan` | x86-64 | `-fsanitize=address,undefined`, no baselines | suite |
| `arm64` | aarch64 | Release, baselines | suite |

Sanitizer jobs skip the baselines, as the local TSan build already does (Boost and moodycamel are
not ours to fix). `FetchContent` downloads (~820 MB unpacked in `build/_deps`, mostly Boost) are
cached by `actions/cache` keyed on the pinned versions. Rough cost: 10–15 minutes per job on two
vCPUs, so 40–60 minutes per push, ~40 pushes a month within the free 2,000 while private. If that
binds, the sanitizer jobs move to pull requests and `main` only.

**The tests assume dev-lnx01. Three changes make them portable:**

1. *CPU choice.* Many tests pin to CPU 2 and 3 (the defaults in `load_config`, the clock overhead
   and noise checks), `placement_test` looks for a CPU on another node, and `cross_cpu_test` walks
   every online CPU. On a 2-vCPU runner only CPUs 0 and 1 exist. A small test helper takes CPUs
   from the process's affinity mask (`sched_getaffinity`), preferring dev-lnx01's reserved CPUs
   when present, so on dev-lnx01 the tests do exactly what they do now. A check that needs more
   CPUs or another node than the machine has is reported as skipped (CTest `SKIP_RETURN_CODE`),
   never passed silently. The benchmarks' defaults do not change.
2. *Quiet-machine checks.* Some live checks assert timing that a shared VM cannot promise: noise
   S4 (injected stops measured within 1 µs), `cross_cpu_test`'s "no pair proves disagreement on
   this machine", calibration spread. These get the CTest label `quiet`; CI runs `ctest -LE
   quiet`, dev-lnx01 runs everything. The logic checks in the same tests (synthetic inputs) stay
   unlabelled and run everywhere, so a test is split if it mixes both. The exact list is settled by
   running on the runners, and recorded in Review.
3. *Parallel safety.* Found while drafting: `ctest -j2` on dev-lnx01 fails noise S4, because two
   tests pin to CPU 2 at once. Tests that pin get the CTest `RESOURCE_LOCK cpu`, so they never
   overlap; the rest run in parallel.

**ARM.** The non-x86 clock is a `steady_clock` fallback that refuses to publish. It has compiled
but never run. On ARM, tests that need a calibrated TSC (calibration, clock block, record cost)
must expect the refusal and check its reason, not fail; queue, shared-memory and histogram tests
run unchanged and are the point of the job. `check_hot_path` stays x86-64 only (it reads x86
disassembly). Note 006's S3 for aarch64 (no barrier instructions beyond `ldar`/`stlr` on the hot
path) is not added here: a separate decision.

**Results checks need no machine.** `report --check` and `run_py_test.py` read committed JSON and
markdown only; they run in the `x64` job as on dev-lnx01. The environment checker is not run
against the runner: it would rightly refuse it.

## Spec

- S1. Every push and pull request to `main` runs the four jobs; any failure fails the workflow.
- S2. Every job builds with `-Werror`, using the Ubuntu 26.04 archive's gcc 15 and CMake 4.
- S3. On a 2-CPU, 1-node runner every test passes or is reported skipped with its reason; no test
  passes by doing nothing. On dev-lnx01, the full suite (`quiet` included) still passes and pins
  the same CPUs as before.
- S4. `ctest -j` passes on dev-lnx01 (no two pinning tests overlap).
- S5. On aarch64 the queue, shared-memory, load and histogram tests run and pass; TSC-dependent
  tests check the fallback's refusal.
- S6. TSan and ASan/UBSan jobs run the whole unlabelled suite clean.
- S7. `report --check` runs in CI; a deliberately stale README fails the workflow (shown once on a
  throwaway branch).
- S8. No benchmark runs in CI, and nothing in CI writes to `results/`.
